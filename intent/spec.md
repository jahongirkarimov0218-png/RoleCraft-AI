## 1. Цель (одно предложение)

Добавить в существующее Next.js-приложение **одну статическую HTML-страницу**. Она показывает вердикт о выбранной нише (одна из двух), причины выбора и 2-недельный тест с заранее заданным порогом «идём / переходим ко второй нише». Каждое числовое и фактическое утверждение на странице подкреплено источником или явно помечено как предположение.

**Финальное условие успеха.** Рома открывает страницу в браузере и видит:
- ровно одну нишу;
- не больше трёх причин её выбора;
- тест с числовым порогом.

После этого он может начать тест, не возвращаясь к анализу (intent → «Какой результат нужен»). Если страница сводится к выводу «все ниши интересны», это провал.

### 2.2 FACT — из intent (дословный смысл, без интерпретации)
- Сравниваются **два** рынка: операционная работа клиник и B2B-маркетинг для владельцев МСБ. ИИ — инструмент внутри продукта, а не ниша.
- Рынок — Узбекистан. Запас без выручки — не больше 3 месяцев. Ручные продажи допустимы для первых 10–20 клиентов.
- Результат — отчёт на одну страницу в браузере: вердикт, причины, тест на 2 недели с порогом.
- Не входит в задачу: клинические функции, B2C wellness, «ИИ-продукты» как рынок, прошлые разборы 1000+ стартапов как данные, венчурный путь, **идея конкретного приложения**.

### 2.3 ASSUMPTION — требуют подтверждения
| # | Предположение | Почему так | Кто подтверждает |
|---|---|---|---|
| A1 | «Интеграция в кодовую базу» означает новый маршрут в этом же Next.js-приложении, а не отдельный сайт | Так сформулирован запрос | Рома |
| A2 | Отчёт — личный документ основателя, не предназначенный для публики | В intent есть личные ограничения: запас ≤3 мес., «продавать мне сложно» | Рома (→ C-01) |
| A3 | Язык отчёта — русский | intent написан по-русски, но это открытый вопрос Q8 в intent | Рома |
| A4 | «Срок до первых денег» — критерий с наибольшим весом | Следует из ограничения «≤3 месяцев без выручки». В самом intent веса не заданы | Рома |
| A5 | Содержимое отчёта (исследование рынка) готовит аналитик или ИИ-ассистент **до** сборки и кладёт его в типизированный файл данных. Приложение ничего не генерирует во время работы | Нужна доказательность, ИИ-генерация в рантайме даёт непроверяемые факты (→ D-02) | Рома / тимлид |

## 3. Границы

### 3.1 Входит
- Новый маршрут со статической страницей отчёта.
- Типизированный контракт данных отчёта и валидатор его инвариантов.
- Unit-тесты валидатора и E2E-тесты страницы (десктоп и мобильный).

### 3.2 Не входит (явно)
- LLM-вызовы, новые API-роуты, формы ввода, хранение данных, аналитика посещений.
- Аутентификация и пользователи. Если нужна настоящая приватность, это отдельная задача (→ C-01).
- Исправление пред-существующих проблем: F4 (`unsafe-eval`), F5, F8, F9. Они перечислены в §10 как риски, но **не правятся в этом PR**, чтобы не расширять его.
- Само исследование рынка — содержательная работа, а не код. Её процесс описан в §7, но это отдельный трек.
- Любые выводы о нишах и идеи приложения в этой спецификации.

## 4. Требования

### 4.1 Функциональные

| ID | Требование | Трассировка к intent | Проверка |
|---|---|---|---|
| R-01 | Страница доступна по маршруту `/niche-report` и открывается в браузере без JS-зависимостей (Server Component, статический рендер) | «отчёт на одну страницу, которая открывается в браузере» | E2E: `GET /niche-report` → 200 при включённом флаге |
| R-02 | Первый экран показывает **ровно одну** выбранную нишу | «вердикт: одна ниша» | Валидатор V-03; E2E: один `[data-testid=verdict]` |
| R-03 | Под вердиктом — от 1 до 3 причин, каждая со ссылкой на критерии матрицы | «причины, почему выбрана она» | V-04 |
| R-04 | Блок теста: длительность 14 дней, аудитория (тёплая), действие, метрика, **числовой** порог, правило «если ≥ порога — идём, иначе — вторая ниша» и название второй ниши | «тест на 2 недели … с заранее заданным порогом» | V-06, V-07 |
| R-05 | Компактная матрица: 2 кандидата × N критериев, у каждого критерия вес и обоснование, у каждой оценки — доказательство | Блокер интервью — «нет критериев» | V-01, V-02, V-05 |
| R-06 | Каждое фактическое утверждение помечено как FACT (с источником и датой обращения), ASSUMPTION или UNKNOWN. Метка видна на странице | Раздел «Открытые вопросы»: не додумывать | V-08, V-09 |
| R-07 | Отдельный короткий блок «Что осталось неизвестным» — нерешённые вопросы из intent, которые влияют на вывод | Раздел «Открытые вопросы» | V-10 |
| R-08 | Кандидаты — только `clinic-ops` и `smb-marketing`. Клинические функции, B2C wellness и «ИИ-продукты» как рынок на странице не оцениваются | «Ограничения», «Что не входит» | V-02 |
| R-09 | Тест сформулирован как проверка **проблемы и готовности платить**, без описания конкретного продукта или фичей | «Идея конкретного приложения» не входит (→ C-04) | Ревью контента + V-11 (запрещённые слова) |

## 5. Архитектурные решения

### D-01 — Где живёт страница: route group с отдельным корневым layout

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| A. `src/app/niche-report/page.tsx` под текущим корневым layout | Ноль рефакторинга | Сверху будет шапка «Customer Feedback AI» и ссылка на GitHub (F2); `<html lang="en">` на русском тексте; печать зависит от глобального скрытия `header` | Отклонён как вариант по умолчанию |
| **B. Route groups:** перенести `layout.tsx` и `page.tsx` в `src/app/(main)/`, отчёт — в `src/app/(report)/niche-report/` со своим корневым layout | Чистый брендинг отчёта, корректный `lang`, URL существующих страниц не меняются | Перенос двух файлов; несколько корневых layout'ов в Next.js дают полную перезагрузку при переходе между группами (здесь это неважно, ссылок между ними нет) | **Рекомендован** |
| C. Отдельный статический HTML вне Next.js | Максимальная изоляция и приватность | Это не «интеграция в кодовую базу» (A1), не переиспользуются токены и тесты | Запасной вариант, если C-01 решится в пользу полной приватности |

Структура после D-01 (вариант B):
```
src/app/
├── (main)/
│   ├── layout.tsx            # перенесён без изменений из src/app/layout.tsx
│   └── page.tsx              # перенесён без изменений из src/app/page.tsx
├── (report)/
│   ├── layout.tsx            # новый: <html lang="ru">, Inter, globals.css, без Header/Footer
│   └── niche-report/
│       └── page.tsx          # Server Component, рендерит NICHE_REPORT
├── api/…                     # без изменений
└── globals.css               # без изменений
```
Риск переноса: импорты через `@/` не меняются, относительный импорт `./globals.css` превращается в `../globals.css`. Проверка — `npm run build` и полный прогон E2E на `/`.

### D-02 — Содержимое страницы: статические данные, никакой генерации в рантайме

- Данные лежат в `src/lib/niche-report/report-data.ts` как `export const NICHE_REPORT: NicheReport`.
- Отклонено: LLM-генерация через новый API-роут. Она добавляет поверхность атаки, расходы и ключи, а главное — даёт непроверяемые факты, что противоречит R-06. Fallback-движок (ADR-0002) здесь тоже неприменим: эвристический вердикт о бизнес-нише хуже, чем отсутствие вердикта.
- Отклонено: Markdown или MDX. Нужны типобезопасность и машинная проверка инвариантов, а MDX — лишняя зависимость.

### D-03 — Контракт данных

```ts
// src/lib/niche-report/types.ts
export type CandidateId = "clinic-ops" | "smb-marketing";
export type EvidenceKind = "fact" | "assumption" | "unknown";

export interface Source {
  title: string;
  publisher: string;
  url: string;          // только https:
  accessedAt: string;   // ISO-дата обращения к источнику
}

export interface Evidence {
  claim: string;
  kind: EvidenceKind;
  source?: Source;      // обязателен при kind === "fact"
}

export interface Criterion {
  id: string;
  label: string;
  weight: number;       // 0..1, сумма по всем критериям = 1
  rationale: string;    // почему такой вес, со ссылкой на ограничение из intent
}

export interface Score {
  criterionId: string;
  value: 1 | 2 | 3 | 4 | 5;
  evidence: Evidence[]; // минимум 1
}

export interface Candidate {
  id: CandidateId;
  label: string;
  scores: Score[];      // ровно по одному на каждый критерий
}

export interface ValidationTest {
  durationDays: 14;
  audience: string;
  action: string;       // что делает Рома (без описания продукта, → C-04)
  metric: string;
  threshold: { value: number; unit: string };
  goRule: string;       // "если ≥ порога — идём"
  fallbackCandidateId: CandidateId;
}

export interface NicheReport {
  meta: { title: string; author: string; status: "draft" | "final"; generatedAt: string; version: string };
  verdict: { candidateId: CandidateId; reasons: { text: string; criterionIds: string[] }[] };
  criteria: Criterion[];
  candidates: [Candidate, Candidate];
  test: ValidationTest;
  unknowns: string[];
}
```

### D-04 — Валидатор инвариантов: чистая функция, тестируется в Vitest

`src/lib/niche-report/validate.ts` → `validateNicheReport(r): string[]` (пустой массив = валидно). Unit-тест прогоняет его на реальном `NICHE_REPORT`. **Поэтому невалидный контент ломает `npm test`, а не попадает на страницу.**

| ID | Инвариант |
|---|---|
| V-01 | Сумма `criteria[].weight` = 1 (±0.001); каждый вес в (0, 1]; `id` критериев уникальны |
| V-02 | Ровно 2 кандидата, их id — ровно `{clinic-ops, smb-marketing}`; у каждого по одной оценке на каждый критерий |
| V-03 | `verdict.candidateId` — один из кандидатов **и** у него строго максимальная взвешенная сумма. При равенстве — ошибка: вердикт должен быть однозначным |
| V-04 | Причин 1–3; каждая ссылается хотя бы на один существующий критерий |
| V-05 | У каждой оценки ≥1 доказательство |
| V-06 | `test.durationDays === 14`; `threshold.value` — конечное число; `unit` не пустой |
| V-07 | `test.fallbackCandidateId !== verdict.candidateId` |
| V-08 | Каждое `kind: "fact"` имеет `source` с `url`, начинающимся на `https://`, и валидную `accessedAt` |
| V-09 | `accessedAt` не старше 180 дней относительно `meta.generatedAt` (свежесть, → K-02) |
| V-10 | Если хоть одно доказательство помечено `unknown`, то `unknowns.length ≥ 1` |
| V-11 | В `test.action` и `test.metric` нет запрещённых маркеров идеи продукта (список задаётся в валидаторе: «приложение», «бот», «фича», «MVP», «функционал»; → C-04) |
| V-12 | Видимый текст ≤ 700 слов (считается по всем строковым полям, кроме URL; → N-07) |

### D-05 — Закрытие страницы от публичного доступа (вытекает из C-01)

- `page.tsx`: если `process.env.NICHE_REPORT_ENABLED !== "true"`, вызывается `notFound()`. Значение по умолчанию — выключено.
- Страница статическая, поэтому флаг читается **во время сборки**: чтобы его поменять, нужна пересборка. Это зафиксировать в ADR-0004.
- Плюс `export const metadata = { robots: { index: false, follow: false } }`.
- В `.env.example` добавляется `NICHE_REPORT_ENABLED="false"` с комментарием о том, что это **не** механизм приватности.
- Для E2E: в `playwright.config.ts` у `webServer` добавить `env: { NICHE_REPORT_ENABLED: "true" }`. Риск: при `reuseExistingServer: true` уже запущенный dev-сервер без флага даст 404. Это нужно описать в README тестов.

## 6. UX и раскладка страницы

Одна колонка `max-w-3xl`, отступы кратны 8px, фон `slate-50`, карточки `bg-white border-slate-200/80 shadow-card`.

```
┌───────────────────────────────────────────────┐
│ Мета-строка: Автор · Статус · Дата · Версия    │  text-xs slate-500, tabular-nums
├───────────────────────────────────────────────┤
│ H1  Вердикт: <ниша>                            │  data-testid=verdict
│ 1–3 причины (каждая → бейджи критериев)        │
├───────────────────────────────────────────────┤
│ Тест на 14 дней                                │  data-testid=validation-test
│ Аудитория · Действие · Метрика                 │
│ Порог: ≥ <число> <ед.>  → идём                 │  tabular-nums, крупно
│ Иначе → <вторая ниша>                          │
├───────────────────────────────────────────────┤
│ Матрица: критерий | вес | ниша A | ниша B      │  <table>, tabular-nums
│ (сноски-доказательства под таблицей,           │
│  бейджи FACT / ASSUMPTION / UNKNOWN)           │
├───────────────────────────────────────────────┤
│ Что осталось неизвестным (≤5 пунктов)          │
├───────────────────────────────────────────────┤
│ Источники (нумерованный список, дата обращения)│
└───────────────────────────────────────────────┘
```

Решения по UX:
- **Порядок «вердикт → тест → матрица»** — сознательный. Цель — остановить анализ. Поэтому действие (тест) идёт выше обоснования (матрицы). Если матрица окажется первой, получится ещё один разбор.
- **Цвета бейджей:** FACT — `status.positive`, ASSUMPTION — `status.neutral`, UNKNOWN — `status.negative`. Рядом всегда текстовая метка (N-06). Вердикт **не** подсвечивается зелёным: цвет не должен изображать уверенность, которой нет.
- **Без графиков:** таблица 2×N читается быстрее. Если позже понадобится визуализация весов, перед реализацией нужно загрузить навык `dataviz`.
- **Кнопка «Печать / PDF»:** опциональна, client-компонент `.tactile-btn`, вызывает `window.print()`, скрывается в печати. Переиспользовать `triggerCleanPdfExport` нельзя: он подставляет в заголовок суффикс «RoleCraft Enterprise Specification» (`src/lib/rolecraft/export-pdf.ts`).
- **Без `<header>` и `<footer>` внутри контента:** глобальное правило печати (F6) скроет их. Для мета-строки используется `<div>` или `<p>`.
- **`.dark` не используется:** в приложении нет переключателя, отчёт только в светлой теме (F7).

## 7. Процесс подготовки контента (исследовательский трек)

Не код, но это блокер релиза: без валидных данных страница не проходит V-01…V-12.

1. **Закрыть блокирующие вопросы** из §11 (Q-01, Q-02, Q-04, Q-10) с Ромой. Без них порог теста и веса придуманы, а не выведены.
2. **Собрать данные по Узбекистану** только из проверяемых источников. Для каждой цифры: URL, издатель, дата обращения. Данные, которых нет в открытом доступе, помечаются `assumption` или `unknown`, а не оцениваются «на глаз».
3. **Запрещено:**
   - выдумывать цифры, источники или цитаты;
   - использовать разборы 1000+ стартапов (исключены intent'ом);
   - описывать продукт или фичи.
4. **Заполнить `report-data.ts`**, прогнать `npx vitest run`, исправить нарушения инвариантов.
5. **Ревью Ромой**, перевод `meta.status` в `"final"`.

## 8. Тестирование, критерии приёмки и DoD

### 8.1 Unit (Vitest), новый файл `test/niche-report.test.ts`
- Валидатор: по одному негативному кейсу на каждый инвариант V-01…V-12 и один позитивный фикстурный отчёт.
- Реальный `NICHE_REPORT` проходит валидатор. Пока `meta.status === "draft"`, проверяются только структурные инварианты V-01…V-07. При `"final"` проверяются все V-01…V-12. `skip` и `only` в этом файле запрещены (→ K-05).

### 8.2 E2E (Playwright), новый файл `e2e/niche-report.spec.ts`, оба проекта
1. `/niche-report` → 200, `h1` содержит название ниши, `[data-testid=verdict]` ровно один.
2. Порог теста виден и содержит число.
3. Нет горизонтального скролла на 375px (`scrollWidth <= clientWidth`).
4. `emulateMedia({ media: "print" })`: кнопки скрыты; высота контента ≤ высоты одной A4 при заданных полях (проверка по `document.body.scrollHeight` с пересчётом из CSS px). Это эвристика, итог подтверждается ручной печатью (→ K-06).
5. Все внешние ссылки имеют `rel="noopener noreferrer"` и `https:`.
6. Регрессия: существующие `e2e/rolecraft.spec.ts` и `e2e/product-flow.spec.ts` зелёные после переноса в `(main)`.
7. Без флага `NICHE_REPORT_ENABLED` маршрут отдаёт 404. Проверяется отдельным билдом в CI или unit-тестом функции-гарда — выбрать один способ.

### 8.3 Definition of Done
- [ ] `npm run build` без ошибок.
- [ ] `npx vitest run`: 62 существующих теста + новые, все зелёные.
- [ ] `npx playwright test`: все сценарии зелёные на Desktop Chrome и Pixel 5.
- [ ] Ручная печать в Chrome → ровно 1 страница A4 (скриншот приложен к PR).
- [ ] `security-review` прогнан по diff, находки закрыты или обоснованы.
- [ ] ADR-0004 добавлен; `AGENTS.md` обновлён: структура, счётчики тестов, `NICHE_REPORT_ENABLED`.
- [ ] Решения по C-01…C-06 записаны с именем принявшего.
- [ ] Ни одна строка в `report-data.ts` с `kind: "fact"` не осталась без источника (гарантирует V-08).

«Готово» можно заявлять только при выполнении всех пунктов **с приложенными выводами команд**.
